DESIGN.md가 뭔가요
쉽게 말하면 우리 서비스의 디자인 규칙을 통째로 AI에게 넘겨주는 설명서(md문서)입니다.
AI에게 그냥 "이런이런 화면 만들어줘"라고 하면, 당연히 우리 서비스를 모르니까 그때그때 다른 스타일에 저퀄 결과물이 나옵니다.
그런데 DESIGN.md를 같이 건네주면, AI가 그 안에 정리된 컬러 · 폰트 · 간격 · 버튼 모양 같은 규칙을 읽고 우리 서비스 톤에 맞게 화면을 만들어냅니다.

CLAUDE.md가 AI에게 "이 프로젝트의 코딩 규칙은 이런 식이야"라고 알려주는 문서라면,
DESIGN.md는 "이 서비스의 디자인 규칙은 이런 식이야"라고 알려주는 문서인 셈입니다.

참고로 업계에서는 이걸 "AI 시대의 Bootstrap 자리를 누가 먼저 선점하느냐" 경쟁으로 보는 시각도 있다고 합니다.
디자인 시스템 표준을 먼저 정한 쪽이 이기는 싸움이라는 거죠..!!

저희도 바로 쓸 수 있을까요?
>>> 가능합니다!!
사용하는 법
기존 프로젝트 루트에 DESIGN.md 파일을 하나 두고, Claude Code나 Cursor에게 "이 파일 참고해서 UI 만들어줘"라고 하면 끝입니다.
설치할 도구도 없고, 우리가 쓰고 있는 CLAUDE.md(개발 규칙)와 역할이 겹치지 않아서 같이 둬도 문제없습니다.
우리 서비스만의 DESIGN.md 만드는 법
처음부터 DESIGN.md를 직접 작성할 필요는 없습니다.
아래 프롬프트를 코드 레포가 연결된 Claude Code나 Cursor에 그대로 던지면 기존 코드베이스를 분석해서 DESIGN.md 초안을 뽑아줍니다.
 Analyze the design system of this codebase with the goal of creating a DESIGN.md file in the project root and giving the user a file for easy copy & pasting.

Reference material:
  Overview : https://stitch.withgoogle.com/docs/design-md/overview/
  Format   : https://stitch.withgoogle.com/docs/design-md/format/
  Spec     : https://github.com/google-labs-code/design.md

Examples from the spec repo:
  https://github.com/google-labs-code/design.md/blob/main/examples/atmospheric-glass/DESIGN.md
  https://github.com/google-labs-code/design.md/blob/main/examples/paws-and-paths/DESIGN.md

Requirements:
- Begin with YAML frontmatter containing all structured design tokens
  (colors, typography, spacing, elevation, motion, radii, shadows, etc.)
- Follow with free-form Markdown that describes the look & feel and
  captures design intent that token values alone cannot convey
- The file must be entirely self-contained — do not reference any
  files, variables, or paths from the codebase
- All token values must use valid YAML design token format

If you have access to a running local server or screenshots of the
product, compare your DESIGN.md against the rendered UI. Revise until
both the YAML tokens and the written description faithfully capture
the product's visual identity.
이미 쌓여있는 우리 코드를 그대로 재료로 써서 뽑는 방식이라, 진입장벽이 거의 없습니다.
물론 여기서 얻은 결과물은 초안이니까 디자인에서 한번 훑어봐야겠지만, 백지에서 쓰는 것보다 훨씬 가볍게 출발할 수 있습니다~!

DESIGN.md를 더 가다듬고 싶은 분들을 위한 추가 꿀팁을 드리면,
Playwright(브라우저 MCP)를 사용해서 AI가 실제 서비스 화면에 접근해 대조해서 문서를 개선할 수 있습니다.
그렇게 해서 나온 프로젝트 서비스의 DESIGN.md 결과물은 파일로 첨부해뒀으니 어떤 느낌의 문서인지 보고싶은 분들은 참고해주세요~

실제로 돌려봤습니다
마침 최근에 프로젝트에서 v4.7 타겟으로 대시보드 기능을 설계 중이었어서, 바로 실험 대상으로 삼아봤습니다.
Claude Code에게 "이 스펙 설계서와 DESIGN.md를 기반으로 대시보드 컨셉 목업을 만들어줘"라고 던져봤습니다.
*(참고) 대시보드 기능은 프로젝트의 업무 진행 상황을 차트로 조회할 수 있는 뷰 입니다.

Input: DESIGN.md + 스펙 md + 코드베이스 일부 참조
Outout: 


결과는 위와 같은데요! 서비스 전체적인 톤앤매너(컬러 · 타이포)는 확실히 잘 지켜준 것 같습니다.
다만 아이콘을 이모지로 찍고 차트 비율을 감으로 잡아서 그런지... 실제 서비스 화면으로 바로 쓰기엔 조금 어색한 형태로 나왔습니다.

실험에서 깨달은 건 두 가지입니다.
DESIGN.md만 쓰기엔 반쪽짜리다. 토큰(컬러 · 폰트 · 간격) 영역에서의 지침 강제력은 뛰어나지만, "이 서비스의 실제 화면 생김새"를 재현하려면 컴포넌트 코드와 기능 스펙이 함께 있어야 합니다. 웹페이지 수준은 DESIGN.md만으로 충분할 수 있겠으나, 기존 서비스 위에 기존에 없던 컴포넌트로 새 화면을 그려낼 때는 부족함이 아직 있어보입니다.
AI가 백지에서 프로덕션 퀄 화면을 뽑는 건 아직 이르다. 기존 화면과 맞물려야 하는 신규 기능일수록 "기존 컴포넌트를 재활용하라"는 지시가 DESIGN.md 토큰보다 훨씬 큰 기여를 합니다. 이 부분이 당장은 사람의 큐레이션으로 메워져야 할 것 같습니다.

구민님의 AI Native 제안의 마지막 퍼즐..?!
어제 구민님이 제안주신 큰그림을 다시 보면, 입력(Input) 축이 (개발 코드, 스펙 문서, 번역) 3개였습니다. 디자인은 산출물(Output) 쪽에만 존재했고요.
생각해보면 살짝 아쉬운 지점이었습니다. 디자인 시스템도 단일 원본 지식(SSOT)에 포함되어야 자연스러우니까요.



여기서 DESIGN.md가 이 빈 자리를 채워줄 수 있는 가능성이 있지 않을까.. 하는 생각이 들었습니다.
아직은 위 실험 결과를 감안하면 DESIGN.md 하나만으로 디자인 축이 완성되는 건 아니지만,
앞으로 DESIGN.md를 중심으로 Figma 컴포넌트 라이브러리와 시안이 MCP나 skill로 연결된 형태를 갖추게 된다면
개발/기획/디자인 세 축이 전부 문서(+컴포넌트 묶음)로 수렴하는 그림이 나올 수 있을 것 같습니다.
 


정리 — 어디서부터 시작해볼까
DESIGN.md는 "AI 시대의 Bootstrap" 자리를 노리는 흥미로운 시도이고,
AI Native 전환 과정에서 디자인 축의 첫번째 step으로서 시도해볼 가치가 있는듯 합니다.

당장에 DESIGN.md 하나만으로 마법같은 결과가 나오지는 않는다는걸 체감했지만,
어제까지만 해도 몇개월 뒤 이야기처럼 보이던 그림이 생각보다 빨리 현실에 들어오고 있는 것 같기는 합니다..!
